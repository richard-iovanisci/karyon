<objective>
Create `scripts/health-check.sh` and `task health-check`. The script is
read-only, fail-fast, and verifies HEALTH-01..07 plus workload proofs from
DEP-01..03.

Per BLOCKER #4 from checker round 1, the cluster Ready node-wait timeout is
180s (not 60s). The longer budget absorbs the first-pull GPU device-plugin
DaemonSet registering `nvidia.com/gpu` capacity on spoke-ml after a fresh
rebuild — observed to take 60-120s in cold-start measurements. Without this,
the 20-minute rebuild SLO can spuriously fail at the health gate even when the
chain itself ran cleanly.

Per HIGH-2 from cross-AI Codex review (2026-04-28, revision round 2), the
in-hub DNS probe is implemented as `kubectl --context k3d-hub-flux -n
flux-system exec deploy/source-controller -- getent hosts ...`. This is the
only way to satisfy BOTH constraints simultaneously: the read-only contract
(no resource creation/deletion) and the in-hub probe requirement (resolves
spoke hostnames from inside a cluster network). `source-controller` is the
correct probe target because:

1. It's one of the four bootstrap-managed Flux controllers (always present
   after `bootstrap-flux.sh` succeeds — see existing pattern in
   `scripts/bootstrap-flux.sh` lines 256-263 which gates on count == 4).
2. `kubectl exec` into an existing pod creates no new resources and deletes
   none — it satisfies the strict no-`kubectl apply`/no-`kubectl delete` /
   no-`kubectl run` contract.
3. `getent hosts` is the BusyBox/distroless-friendly resolver invocation
   that's available in standard Flux controller images.

The alternative (`kubectl run --rm -it --restart=Never` for a temporary probe
pod) is `apply` + `delete` under the hood and would violate the read-only
contract. That alternative is explicitly forbidden by Plan 01 Task 4's bats
contract (negative grep for `kubectl run`).

Per MED-3, the script must count expected Flux deployments via `kubectl ...
get deploy --no-headers | wc -l` and assert the count is >= 4 BEFORE running
`kubectl wait --for=condition=Available deploy --all`. Without this gate, an
empty result set would cause `wait --all` to return 0 immediately and falsely
report success.
</objective>

<threat_model>
**ASVS Level:** 1
**Block on:** high

- **T-05-09 Health-check mutation:** A mutating health check can hide the system
  state it is supposed to verify. Mitigation: script must not contain `kubectl
  apply`, `kubectl delete`, `kubectl run`, `k3d cluster stop`, or `k3d cluster
  start`. (HIGH-2 fix: `kubectl run` explicitly forbidden — that's the
  temporary-probe-pod pattern that violates the read-only contract.)
- **T-05-10 Misleading DNS status:** Continuing after stale DNS can produce noisy
  downstream failures. Mitigation: DNS gate fails fast with `Fix: task fix-dns`.
- **T-05-11 Wrong-cluster proof:** Checking only spoke resources can miss Flux
  reconciliation failures. Mitigation: hub-side Flux Kustomization Ready checks
  are mandatory before direct workload checks.
- **T-05-19 Spurious health-check timeout:** A too-short cluster Ready timeout
  fails the SLO not from a slow chain but from an unforgiving gate.
  Mitigation: 180s node-Ready timeout, code-comment justifies, bats grep pins
  the literal.
- **T-05-24 Probe-pod read-only contract collision (HIGH-2, NEW in revision
  round 2):** A temporary probe pod (`kubectl run --rm`) is `apply` + `delete`
  and violates the read-only contract. Mitigation: in-hub DNS probe uses
  `kubectl exec deploy/source-controller -- getent hosts ...` — read-only
  exec into an existing Flux controller pod. Plan 01 Task 4's bats contract
  forbids `kubectl run` in this script.
- **T-05-25 Empty-set kubectl wait pass-through (MED-3, NEW in revision round
  2):** `kubectl wait --for=condition=Available deploy --all` returns 0
  immediately when zero deployments match. Mitigation: script counts
  deployments via `kubectl ... get deploy --no-headers | wc -l` and fails fast
  if the count is < 4. Pattern matches existing `bootstrap-flux.sh` lines
  256-263.
</threat_model>
