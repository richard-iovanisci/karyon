<objective>
Create destructive UX wrappers and Taskfile entries: `task destroy` and
`task rebuild`. Preserve the existing cache-safe `scripts/delete-clusters.sh`,
add one-prompt confirmation, run the strict rebuild chain, and enforce the
20-minute warm-cache SLO as a hard failure.

Per WARNING #5 from checker round 1, all chain invocations use the
`bash "${SCRIPT_DIR}/<script>.sh"` form (consistent with the bats grep
contract). Per WARNING #7, `rebuild.sh` writes to `/tmp/karyon-rebuild.log`:
- ordered step markers `>>> step destroy`, `>>> step create-clusters`,
  `>>> step bootstrap-flux`, `>>> step register-spokes`,
  `>>> step deploy-examples`, `>>> step health-check`
- a final line `rebuild elapsed seconds: N`
This log is what the live state-checker bats in `phase5-02-live.bats` reads to
verify the chain ran in order and the SLO was met (no double-rebuild needed).

Per HIGH-1 from cross-AI Codex review (2026-04-28, revision round 2),
`scripts/rebuild.sh` MUST run `kubectl config use-context k3d-hub-flux`
BETWEEN the `create-clusters.sh` and `bootstrap-flux.sh` invocations. Reading
the actual existing scripts confirms the issue:

- `scripts/bootstrap-flux.sh` (line 161): `ctx="$(kubectl config
  current-context ...)"; if [[ "${ctx}" != "${KUBE_CTX}" ]]; then fail ...`
  where `KUBE_CTX="k3d-hub-flux"`. The script EXITS 1 if the current context
  is not `k3d-hub-flux`. It does NOT auto-switch (D-06 read-only assertion).
- `scripts/register-spokes-for-flux.sh` (line 632): same gating pattern.
- `scripts/create-clusters.sh` does NOT pin the current context after creating
  clusters. `k3d cluster create` switches the current context to the last
  cluster it creates. Looking at create-clusters.sh lines 174-176:
  `create_cluster hub-flux 6443 ...; create_cluster spoke-ml 6444 ...;
  create_cluster spoke-apps 6445 ...` — after this completes, current context
  is `k3d-spoke-apps`.

Without an explicit `kubectl config use-context k3d-hub-flux` step in
`rebuild.sh` between `create-clusters` and `bootstrap-flux`, `task rebuild`
will silently fail at the bootstrap step on every fresh run. We do NOT modify
`bootstrap-flux.sh` or `register-spokes-for-flux.sh` (they are completed Phase
3/4 deliverables) — we pin the context once, in `rebuild.sh`, before the chain
runs into the bootstrap step.
</objective>

<threat_model>
**ASVS Level:** 1
**Block on:** high

- **T-05-12 Accidental destruction:** Destroy/rebuild delete local clusters and
  network. Mitigation: require typed `yes` at the outer task unless an explicit
  approved env var is set by `rebuild`.
- **T-05-13 Cache loss:** Docker prune commands would destroy CUDA build cache
  and break the rebuild SLO. Mitigation: wrappers call `delete-clusters.sh` and
  static tests reject `docker system prune`, `docker builder prune`, and
  `docker image prune`.
- **T-05-14 False SLO pass:** A green health-check after 20 minutes fails the
  project core value. Mitigation: `rebuild.sh` exits nonzero if elapsed seconds
  exceed 1200.
- **T-05-20 Unverifiable SLO claim:** Without a structured log, "elapsed
  seconds <= 1200" and "strict chain ran in order" are not automation-
  checkable. Mitigation: `rebuild.sh` writes ordered step markers and an
  elapsed-seconds line to `/tmp/karyon-rebuild.log`, which Plan 06's state
  checker reads.
- **T-05-22 Kube-context drift in rebuild chain (HIGH-1, NEW in revision round
  2):** `bootstrap-flux.sh` (line 161) and `register-spokes-for-flux.sh`
  (line 632) gate on `kubectl config current-context == k3d-hub-flux`. `k3d
  cluster create` switches the current context to the last-created cluster.
  After `scripts/create-clusters.sh` finishes (creates hub-flux, spoke-ml,
  spoke-apps in that order), current context is `k3d-spoke-apps`. Without an
  explicit re-pin, `task rebuild` silently breaks at the bootstrap step.
  Mitigation: `scripts/rebuild.sh` runs `kubectl config use-context
  k3d-hub-flux` BETWEEN the create-clusters and bootstrap-flux steps. Plan 01
  Task 5's bats asserts the literal AND a line-number ordering proving it
  appears strictly between those two invocations.
</threat_model>
