<objective>
Add the DNS repair path: `scripts/fix-coredns.sh` and `task fix-dns`. The
script mutates only `hub-flux`, waits for hub and Flux readiness, and never
restarts spokes or patches CoreDNS directly.

Per WARNING #3 from checker round 1, this plan's contract is verified by
`tests/bats/fix-coredns-01-static.bats` (split out of the prior combined
health bats), so Plan 05-03 can be verified independently of Plan 05-04.

Per MED-2 from cross-AI Codex review (2026-04-28, revision round 2), the
script is now ALLOWED to reference the literals `spoke-ml` and `spoke-apps` —
specifically as DNS probe targets after the hub stop/start completes. This
proves the workaround actually fixed the symptom rather than just running the
mutation in the dark. The negative-grep contract in Plan 01 Task 3 has been
narrowed to forbid only `k3d cluster {stop|start|restart} spoke-*`.

Per MED-3 from the same review, the script must count expected Flux
deployments via `kubectl ... get deploy --no-headers | wc -l` and assert the
count is >= 4 BEFORE running `kubectl wait --for=condition=Available deploy
--all`. Without this gate, an empty result set (e.g., flux-system namespace
exists but the controllers haven't been redeployed yet) would cause `wait
--all` to return 0 immediately and falsely report success.
</objective>

<threat_model>
**ASVS Level:** 1
**Block on:** high

- **T-05-07 Over-broad cluster mutation:** Restarting spokes during DNS repair
  can mask unrelated spoke failures. Mitigation: `fix-coredns.sh` may only run
  `k3d cluster stop hub-flux` and `k3d cluster start hub-flux`. The MED-2
  narrowed contract in Plan 01 Task 3 forbids `k3d cluster {stop|start|restart}
  spoke-{ml|apps}`; merely naming spoke hostnames in DNS probes is
  permissible.
- **T-05-08 Persistent CoreDNS drift:** Editing CoreDNS directly can create
  untracked state. Mitigation: script uses k3d stop/start workaround only and
  static tests reject direct CoreDNS mutation.
- **T-05-25 Empty-set kubectl wait pass-through (MED-3, NEW in revision round
  2):** `kubectl wait --for=condition=Available deploy --all` returns 0
  immediately when zero deployments match. Mitigation: script counts
  deployments via `kubectl ... get deploy --no-headers | wc -l` and fails fast
  if the count is < 4 (source-controller, kustomize-controller, helm-controller,
  notification-controller). Pattern matches existing `bootstrap-flux.sh` lines
  256-263.
</threat_model>

- Section `hub-flux stop/start`: run `k3d cluster stop hub-flux` then

- Section `Flux readiness` (MED-3 deploy-count gate REQUIRED):
  
  1. **Deployment-count gate (MED-3):**
     ```bash
     # MED-3: count deployments BEFORE kubectl wait --all to prevent empty-set
     # trivial pass. Pattern matches scripts/bootstrap-flux.sh lines 256-263.
     deploy_count="$(kubectl --context k3d-hub-flux -n flux-system get deploy --no-headers 2>/dev/null | wc -l)"
     if [[ "${deploy_count}" -lt 4 ]]; then
       fail "expected >= 4 flux controllers in flux-system, found ${deploy_count}.
          Inspect: kubectl --context k3d-hub-flux -n flux-system get deploy,pod
          Fix:     bash scripts/bootstrap-flux.sh && bash scripts/fix-coredns.sh"
       exit 1
     fi
     ```
     The literal `get deploy --no-headers` AND the literal `wc -l` MUST appear
     in the script (asserted by Plan 01 Task 3's bats).
  
  2. **Wait + flux check:**
     ```bash
     kubectl --context k3d-hub-flux -n flux-system wait \
       --for=condition=Available deploy --all --timeout=180s
     flux --context k3d-hub-flux check
     ```
     The `kubectl wait` line MUST appear AFTER the deploy-count gate above
     (asserted by line-number ordering in Plan 01 Task 3's bats).

- Section `Post-restart spoke DNS probe` (RECOMMENDED, MED-2 — allowed):
  This is an OPTIONAL section. If included, it proves the workaround
  actually fixed spoke DNS resolution by probing from inside an existing
  hub-side Flux pod (read-only — no `kubectl run`, no resource creation).
  
  ```bash
  # MED-2: prove the workaround actually fixed spoke DNS resolution.
  # Read-only probe via kubectl exec into existing source-controller pod
  # (no resource creation, no deletion).
  for spoke in spoke-ml spoke-apps; do
    if kubectl --context k3d-hub-flux -n flux-system exec deploy/source-controller -- \
         getent hosts "k3d-${spoke}-server-0" >/dev/null 2>&1; then
      pass "spoke DNS ok: hub can resolve k3d-${spoke}-server-0"
    else
      warn "spoke DNS still failing for k3d-${spoke}-server-0 after hub-flux stop/start.
         The k3d CoreDNS NodeHosts workaround did not fully resolve. Inspect:
           kubectl --context k3d-hub-flux -n kube-system get cm coredns -o yaml
         Fix: rerun: bash scripts/fix-coredns.sh"
    fi
  done
  ```
  The literal `spoke-ml` and `spoke-apps` may now appear in this script
  (MED-2 — narrow contract); they may NOT appear with `k3d cluster
  {stop|start|restart}`.
