# Phase 2 paused — spoke-ml k3s apiserver never starts

## What happened

On rich@Area-51 (WSL2, Docker 29.4.1, NVIDIA driver 596.21), running `bash scripts/create-clusters.sh` successfully:

1. ✓ Preflight green
2. ✓ `k8s-net` Docker network created (172.30.0.0/16, bridge)
3. ✓ CUDA image present (`karyon/k3s-cuda:v1.34.6-k3s1-cuda12.8.1` — already built and GPU-smoke-verified in 02-04)
4. ✓ `hub-flux` (stock `rancher/k3s:v1.34.6-k3s1`, port 6443) created in ~20 s, SAN verified

Then hung on:

5. ✗ `spoke-ml` (our `karyon/k3s-cuda` image + `--gpus all`, port 6444) — k3d said "Starting node 'k3d-spoke-ml-server-0'" and never advanced. After **14 minutes** the container was still `Up` but `docker logs k3d-spoke-ml-server-0` showed only a kubectl-probe loop:

```
E0424 01:04:47 ... memcache.go:265] "Unhandled Error" err="... dial tcp 127.0.0.1:6443: connect: connection refused"
The connection to the server 127.0.0.1:6443 was refused - did you specify the right host or port?
```

The k3s apiserver inside the spoke-ml node container never came up.

User cancelled and tore down: `k3d cluster delete --all && docker network rm k8s-net`.

## A/B observation (the load-bearing clue)

| Cluster | Image | config.toml.tmpl override | --gpus all | Result |
|---|---|---|---|---|
| hub-flux | rancher/k3s:v1.34.6-k3s1 | none (k3s default) | no | apiserver up in 20 s ✓ |
| spoke-ml | karyon/k3s-cuda:v1.34.6-k3s1-cuda12.8.1 | `default_runtime_name = "nvidia"` (our override) | yes | apiserver never started ✗ |

Both clusters share identical k3s version, identical k3d version, identical k8s-net attachment. The only meaningful differences are (a) the custom base image, (b) the baked `config.toml.tmpl` override, and (c) `--gpus all`.

## Leading hypothesis

`images/config.toml.tmpl` sets `default_runtime_name = "nvidia"` unconditionally under the v3-schema override `[plugins.'io.containerd.cri.v1.runtime'.containerd]`. This means **every** system pod instantiated at k3s boot (CoreDNS, local-path-provisioner, traefik, metrics-server, servicelb) is scheduled to run through the NVIDIA container runtime, not just GPU workloads.

In a nested-docker WSL2 environment the nvidia-container-runtime handshake from *inside* the k3s node container is more fragile than from the host. If any one of those system pods can't launch (nvidia-ctk not on path inside k3s-containerd, config.toml render mismatch, cgroups disagreement, etc.), the k3s startup sequence never reaches "apiserver ready" and we see exactly this pattern: container `Up`, no apiserver, no progress.

**This was previously theoretical** — 02-RESEARCH.md §2.2 argued for the override as the third leg of the 3-part GPU contract. We now have empirical evidence it breaks k3s boot in this environment. The research position needs revision.

## Alternative that should work (to investigate next session)

The device-plugin DaemonSet we ship (`images/device-plugin-daemonset.yaml`) already carries `runtimeClassName: nvidia` in its pod spec. The RuntimeClass resource (`name: nvidia, handler: nvidia`) is also in that same file. GPU workloads can opt into the NVIDIA runtime **per-pod** via `runtimeClassName: nvidia`; the cluster-wide `default_runtime_name` override is not strictly required for GPU capacity to surface, as long as the runtime class is wired.

Propose: **drop the `default_runtime_name` override** from `images/config.toml.tmpl` and leave just `{{ template "base" . }}`. The k3s base template already registers `runtimes.nvidia` when nvidia-container-runtime is present in the image (and it is — our Dockerfile runs `nvidia-ctk runtime configure --runtime=containerd` at build time). The device-plugin DaemonSet's `runtimeClassName: nvidia` opts its own pod into the NVIDIA runtime, which is sufficient to expose `nvidia.com/gpu` as node capacity.
