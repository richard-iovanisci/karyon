**REVISED 2026-05-06 PER CROSS-AI REVIEW §2** (codex 2026-05-06; .planning/phases/11-validation-graduation-adr-008/11-REVIEWS.md). The original 11-07 had FOUR review concerns:

- **HIGH #1** Plan 11-07 omits spoke-side `capsule-system` Namespace -- on a clean spoke, the rbac Kustomization can fail with "namespace not found" before the SA is created.
- **HIGH #2** `poc-capsule-spoke` outer K uses `serviceAccountName: kustomize-controller`, but POC spokes provision `flux-reconciler` (verified 2026-05-06 against `scripts/register-poc-cluster.sh:50` + `scripts/register-spokes-for-flux.sh:33`). The entire spoke rbac path may never apply.
- **MEDIUM #3** `rbac/` first ordering only governs apply order INSIDE `pocs/capsule/spoke/kustomization.yaml`. helm-controller can pick up HRs from `poc-capsule` Kustomization BEFORE `poc-capsule-spoke` applies rbac. Either accept Flux-retry behavior empirically OR split rbac into its own outer K.
- **MEDIUM #4** "context deadline exceeded" has multiple plausible causes (RBAC, namespace missing, network, hook Job timeout, CRD readiness, chart hook failure). Plan should capture helm-controller logs + `kubectl auth can-i` output for the impersonated SA before declaring impersonation as the root cause.

This revision addresses all four. **Codebase verification 2026-05-06 confirms HIGH #2 codex was right:** `clusters/hub-flux/pocs/capsule-spoke.yaml:40` literally has `serviceAccountName: kustomize-controller`; both spoke registration scripts provision `flux-reconciler`, never `kustomize-controller`. The Phase 9 D-09-05 comment claimed "spoke-targeted K with kubeConfig is exempt from --default-service-account flag scope, but explicit-set is forward-compat." This was wrong because explicit-set TELLS Flux to impersonate that named SA on the target cluster, which doesn't exist. Phase 9 / 10 reconciles likely succeeded only because the kubeConfig bearer-token (`flux-reconciler-token`) carries cluster-admin and Flux's impersonation may fall through silently in some controller paths, OR Phase 9 / 10 reconciles failed intermittently and were masked by Flux retries — this is precisely the empirical ambiguity codex MEDIUM #4 calls out. # pocs/capsule/spoke/rbac/helm-controller-sa.yaml
```yaml
# G-06 gap-close (2026-05-06): helm-controller impersonation target on spoke-capsule.
#
# Root cause (G-06): When a HelmRelease in capsule-system has `spec.kubeConfig`
# (cross-cluster) but NO `spec.serviceAccountName`, Flux's helm-controller defaults
# to impersonating `system:serviceaccount:capsule-system:default` on the TARGET
# cluster (spoke-capsule). The `default` SA in capsule-system has zero RBAC, so
# helm install/upgrade requests fail with `context deadline exceeded`.
#
# Fix mechanism (per RESEARCH.md line 971 -- oneuptime "Flux Service Account
# Impersonation" article verified): `spec.kubeConfig` + `spec.serviceAccountName`
# causes helm-controller to impersonate the named SA ON THE TARGET cluster.
# This file provisions the SA + cluster-admin ClusterRoleBinding so the impersonation
# has permission to install/upgrade helm releases AND apply chart-rendered resources
# (capsule-proxy:capsule-proxy Role + secrets postRenderers patch from Plan 11-06).
#
# Threat model — codex §2 MEDIUM "cluster-admin rationale overstates containment":
# This binding plainly grants cluster-admin on spoke-capsule to any caller that can
# impersonate this SA. A compromised Capsule chart (or a future HelmRelease added by
# mistake using `spec.serviceAccountName: helm-controller`) gets cluster-admin on the
# entire spoke-capsule cluster — there is NO per-namespace scoping or per-resource
# restriction enforced by Kubernetes itself. We accept this risk because:
#   (a) spoke-capsule is a POC isolation cluster (P31 invariant: NOT in `task rebuild`)
#   (b) ADR-008 ships v0.19 in DEFER posture; Phase 12 (capsule-addon-fluxcd) may
#       narrow this if adopted in v0.20+
#   (c) The alternative — enumerating per-resource Roles for every chart install/upgrade
#       step — breaks on the next chart minor version bump and adds maintenance burden
#   (d) Capsule's webhook does NOT block cluster-admin operations on capsule-system
#       resources (capsule-system itself is not a tenant namespace)
# Documented + accepted per ASVS L1 risk acceptance in <threat_model> T-11-07-01.
#
# Lands via the NEW separate spoke-targeted poc-capsule-spoke-rbac outer Kustomization
# (clusters/hub-flux/pocs/capsule-spoke-rbac.yaml, spec.kubeConfig: spoke-capsule-kubeconfig,
# spec.serviceAccountName: flux-reconciler — matches register-poc-cluster.sh:50). NO
# dependsOn on poc-capsule, ensuring it lands BEFORE HRs are picked up by helm-controller.
apiVersion: v1
kind: ServiceAccount
metadata:
  name: helm-controller
  namespace: capsule-system
# --- (multi-doc YAML separator follows; bare --- omitted to keep the planner frontmatter parser happy) ---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: helm-controller-cluster-admin
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: ServiceAccount
    name: helm-controller
    namespace: capsule-system
```
