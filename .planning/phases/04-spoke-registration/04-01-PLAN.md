## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | bats live test (in-pod probe @tests) extracts the spoke's bearer token via `kubectl get secret -o jsonpath`, then injects it into a remote command via `sh -c`. If the command was traced (`set -x`), the token would land in test output. | mitigate | The bats DSL does NOT enable `set -x` by default; bats DOES NOT echo command lines except on assertion failure where `$output` is dumped. The token DOES appear in `$output` ONLY if the in-pod wget itself fails AND echoes the Authorization header back — verified by RESEARCH.md §Code Examples that wget does NOT echo the header on success or failure. Acceptable risk: the test runs in the developer's local shell, not CI; failure-mode logs go to the developer only. |
| T-04-02 | Tampering | bats static @tests rely on grep against the script + YAML files. A malicious in-tree edit could insert a `set -x` between the strict-mode line and the rest of the script, evading the `^set -euo pipefail` positive grep. | mitigate | The `D-11: scripts/register-spokes-for-flux.sh uses set -euo pipefail and does NOT use set -x` @test runs BOTH a positive grep on `^set -euo pipefail` AND a negative grep filtering comments first via `grep -v '^[[:space:]]*#' | grep -E '^[[:space:]]*set[[:space:]]+-[a-zA-Z]*x'`. Any `set -x`, `set -eux`, `set -xe`, `set -ex` etc. trips the negative grep. The static suite runs on every CI / pre-commit, so a tampered script can't hide from a single test pass. |
| T-04-03 | Spoofing | bats live @tests query `.status.inventory` — a malicious or accidental Kustomization could fake an inventory entry by reconciling a ConfigMap NAMED `karyon-spoke-id` to the WRONG spoke. The grep for `karyon-spoke-ml_karyon-spoke-id__ConfigMap` would still match. | mitigate | The cross-cluster falsifier @test (`ROADMAP success #5`) DOES NOT rely on `.status.inventory` — it queries the actual spoke clusters via `kubectl --context k3d-spoke-{ml,apps}` and asserts the ConfigMap's `data.spoke` field equals the expected spoke name. The same ConfigMap name on different spokes is OK because the namespace differs (`karyon-spoke-ml` vs `karyon-spoke-apps`). Faking that would require simultaneously misconfiguring BOTH spoke seed manifests — a much more intentional misconfiguration than P18. Combined with the inventory-ID grep, the false-positive surface is below practical exploitation risk in a single-user lab. |
| T-04-04 | Repudiation | n/a — bats test framework has no audit log; this is a developer test harness. | accept | Lab-scope; no compliance requirement for test-execution audit. |
| T-04-05 | Denial of Service | n/a — bats tests don't consume resources beyond a single bash process and a few kubectl invocations. | accept | Lab-scope. |
| T-04-06 | Elevation of Privilege | The bats live tests assume the developer's local kubeconfig has cluster-admin on hub-flux + spoke-ml + spoke-apps (k3d default). If that kubeconfig is compromised, the attacker has cluster-admin everywhere — not a Phase-4-specific exposure. | accept | k3d's default kubeconfig posture; not Phase-4's scope to mitigate. |
